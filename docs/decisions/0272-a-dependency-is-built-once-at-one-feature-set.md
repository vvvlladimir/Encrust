# 0272. A dependency is built once, at one feature set

- **Status:** Accepted
- **Date:** 2026-10-14

## Context

After 0207 a run that changed nothing is 23 s, but a dependency bump still cost hours of
checking. The tests were not the cost; each binary finished in under a tenth of a second.
Three things were measured on one bump.

Cargo turns on a dependency's features by what is being built, so `cargo test -p format-cws`
and `cargo test -p encrust-app` build `serde`, `getrandom`, `image` and the rest at different
feature sets, and every variant is a separate build. Right after a `cargo clean -p
printer-profiles`, five builds of that one crate were back in `target/`. Checking crate by
crate, as `workflow.md` asked, rebuilt the dependency tree once for each crate.

Nothing ever left `target/`: `target/debug/deps` held 431 401 files, every old version
of every dependency since the last clean, and listing it took over two minutes.

The editor's language server ran `cargo check --workspace --all-features` in that same
directory, so a check from the terminal waited on its lock.

## Decision

A `workspace-hack` crate generated by `cargo hakari` 0.9 holds each third-party dependency
at the union of the features the workspace uses, on macOS, Linux and Windows, and every crate
depends on it. It leaves out `objc2` and `block2`, because a core crate must not carry the
Objective-C runtime (rule 1), and `ureq`, because TLS stays the window's alone (0172). CI
runs `cargo hakari generate --diff` and `cargo hakari manage-deps --dry-run`.

A change to `Cargo.lock` or to a manifest's dependencies is checked once over the whole
workspace, not crate by crate, and then `cargo sweep --time 7` clears what it left behind.
One cargo runs at a time in a checkout, and the editor builds in its own directory.

## Consequences

Every `-p` build reuses one build of each dependency, so checking crate by crate costs no
more than the crates themselves. After a bump the tree is built once.

A crate built alone now compiles the union, so the first build of a small crate such as
`core-geometry` is heavier than before. A binary carries every feature some other crate
asked for: on macOS the command line's `image` now carries TIFF, as the window's does.
Neither changes what a sliced file contains.

`workspace-hack/Cargo.toml` is generated and has to be kept current. A dependency bump that
moves a feature set fails CI until someone runs `cargo hakari generate` on that branch;
dependabot does not. Reopen this if that happens on most bumps, or once Cargo's own
`feature-unification = "workspace"` setting is stable on the pinned toolchain, which would
replace the crate with one line.

## Alternatives considered

### Cargo's `feature-unification` setting

Same effect with no generated crate (RFC 3692), but it is not stable on the pinned toolchain,
and the toolchain is not moved for a check's speed.

### Only check the whole workspace, always

One feature set too, with no new crate. It makes every one-crate edit pay for the whole
graph, which is what `workflow.md` and the hook exist to prevent.

### The option that won, and what it costs

A generated crate in every manifest, a tool every contributor and CI installs, and a CI step
that fails dependabot's pull requests now and then. Two features have to be held out by
name, and the list must grow if another crate ever needs one kept to itself.
